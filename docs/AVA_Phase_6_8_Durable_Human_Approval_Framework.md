# AVA Phase 6.8 — Durable Human Approval Framework

## Objective and scope

Phase 6.8 adds an AVA-owned backend framework for durable approvals of normalized tool operations. It adds contracts, lifecycle service logic, in-memory and SQLite repositories, and the v0026 migration. It does not add approval routes or UI, dispatch, runtime integration, or execution continuation.

The checked-in Phase 6 outline uses an older sequence. This implementation follows the owner-approved sequence in the Phase 6.8 brief: Phase 6.7 is Workspace Access Management, Phase 6.8 is the Durable Human Approval Framework, and Phase 6.9 is Approval Management UI. The locked canonical plan was not changed.

## Contracts and persisted record

`ava.contracts.approvals` defines `ApprovalRequest`, `ApprovalDecision`, `ApprovalStatus`, `ApprovalReason`, `ApprovalDecisionMetadata`, and `ApprovalRecord`, plus AVA-owned human-decision and invocation-resolution ports.

An approval record binds one run and invocation to the Phase 6.6 `ToolOperationBinding`, tool/version, policy version, feature configuration version, Workspace identity/authorization reference/configuration revision, and trusted execution-authority revision. It stores a safe tool-name summary and timestamps. It does not store operation arguments, credentials, or Workspace root paths. The approval ID is generated by AVA. A unique invocation constraint prevents a second approval history from being created for the same invocation.

The service accepts an invocation request, then calls the existing `ToolPolicyService` itself. It creates a record only if current policy returns `REQUIRES_APPROVAL`, the run exists and remains active, and the trusted authority/Workspace context still matches. It does not accept a caller-supplied policy decision. A repeated request for the exact same pending fingerprint is idempotent; another operation or a terminal approval for that invocation conflicts.

## Lifecycle and decisions

The state machine is `PENDING → APPROVED | DENIED | EXPIRED | CANCELLED | INVALIDATED`. All resolved states are terminal. SQLite and the in-memory adapter resolve records with compare-and-set; a concurrent loser sees the winning resolution, and conflicting terminal choices return a deterministic conflict. Repeating the same human decision is idempotent and never repeats execution.

Expiration is lazy: reads, decisions, and validity checks transition due pending records to `EXPIRED`. The default lifetime is 15 minutes, configurable at service construction. No scheduler was added.

Human decisions use `ApprovalDecisionAuthorityPort`, which resolves the current principal and Workspace scope from server-side context. The decision payload contains no user ID or role flag. Missing authority, invalid authority, or a human outside the record’s Workspace scope fails closed. Read methods exposed by the service also require current scoped human authority and hide records outside that scope.

Production composition has no trusted human-identity adapter and no production tool-execution-authority provider. It composes the approval service with the default-denying human authority and no execution authority. It exposes no approval endpoints, so clients cannot request, list, approve, deny, or cancel approvals through HTTP in this phase.

## Exact operation and current eligibility

Before a decision, cancellation, or validity check, the service re-evaluates the current invocation through `ToolPolicyService` and compares the resulting operation binding, tool definition version, feature configuration version, policy version, authority revision, Workspace authorization reference, and Workspace configuration revision. It also verifies current run state and cancellation intent. An approved record is a historical decision, not an execution token; `remains_valid` returns only a boolean fact and never grants execution.

The current operation is held only in service memory after an approved request, or may be re-established through the optional AVA-owned `ApprovalInvocationResolverPort`. Raw arguments are absent from durable approval rows. No production invocation resolver exists yet. After restart, a pending record remains durable and historically inspectable, but the service invalidates it when it cannot re-establish the current invocation and its eligibility. A future invocation source can preserve it by providing a fresh current request for policy revalidation.

## Persistence and run integration

`ApprovalRepository` is the service boundary. `ApprovalStore` is the thread-safe in-memory adapter. `RelationalApprovalRepository` uses the shared `SqliteDatabase`; it validates records on write and checks indexed identity/status fields against the serialized record on read, failing closed on corrupt or inconsistent data.

Migration v0026 creates `approval_records` with a stable primary key, unique invocation ID, run and Workspace lookup fields, constrained status, request time, and serialized AVA record, with indexes for pending approvals by run and Workspace. The schema does not store tool arguments.

The service verifies run existence and activity at creation and rechecks run status/cancellation before resolution. Existing `RunService.cancel_run` invokes the approval cancellation hook, and a trusted Workspace configuration update invokes Workspace invalidation. Tool-feature configuration updates invalidate pending approvals. Policy, authority, or Workspace changes without a direct hook are detected during lazy revalidation. Invalidated records remain in persistence for history.

This step does not change run status semantics or add an approval event writer. Although the run-event vocabulary already includes `approval_requested`, AVA has no durable normalized `ToolRequested` lifecycle source or transaction boundary spanning run events and approvals. A future agent/invocation integration must establish that source and its atomic event/approval relationship before adding continuation. No paused scheduler, `WAITING_FOR_APPROVAL` transition, or execution continuation was added.

## Limitations and Phase 6.9 readiness

The approval framework and durable storage seam are in place, and current policy is always rechecked before resolution. The production app intentionally cannot create or resolve approvals until it receives trusted tool-execution authority, authenticated human identity and Workspace-scoped decision authority, and a trusted source for current invocation requests. No API endpoint is present, so an approval UI cannot yet safely read or submit decisions against production composition.

Phase 6.9 may proceed with the UI contract/design work, but production decision flows require those trusted backend adapters and the minimal protected read/decision API. This implementation stops at Phase 6.8.
