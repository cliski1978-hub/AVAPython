# AVA Phase 6 — Production Execution Integration Addendum

**Status:** Owner-approved additive plan extension (2026-10-14)
**Applies after:** Phase 6.14 Run Inspector and Tool Activity
**Applies before:** Phase 6.15 Security and Integration Testing

This addendum preserves the existing Phase 6 scope and sequence while assigning the operational security prerequisites identified by the Phase 6.13 lifecycle review. It does not replace earlier phase definitions and does not itself implement or accept any prerequisite. Production normalized tool dispatch remains default-deny until Phase 6.14A–6.14D are implemented and validated.

## Numbering clarification

The legacy `AVA_PHASE_6_IMPLEMENTATION_OUTLINE.md` labels persistence/Run Inspector as 6.11 and final security validation as 6.12. The later implementation records use 6.11 for initial tool implementations, 6.12 for runtime integration, 6.12A for the mode selector, 6.13 for durable lifecycle, and 6.14 for Run Inspector. Both historical records remain intact; this addendum does not renumber completed work. The inserted steps below follow the later implementation sequence. Phase 6.15 remains security and integration testing, and Phase 6.16 remains final validation and handoff.

## Production security prerequisite register — post-6.14A assignment

The following four deployment prerequisites remain open after the Phase 6.14A contract and authority foundation. These assignments clarify ownership within the approved additive sequence; they do not mark future work complete or authorize production dispatch.

| Prerequisite | Responsible phase | Security purpose | Dependencies | Acceptance criteria | Current implementation status | Activation blocker |
|---|---|---|---|---|---|---|
| Production identity provider and exact-session validation | **6.14D**, required before activation | Prove the caller's identity from server-verified evidence and reject forgery, expiry, and revocation | Supported deployment profile, provider configuration/secret management, `HttpPrincipalResolverPort`, `PrincipalValidityPort`, tenant mapping | At least one supported production path validates authenticated requests and exact session/token validity; forged, expired, revoked, missing, and provider-error cases deny; no test principal is used for production | Provider-independent contracts and fail-closed defaults exist; no operational provider or revocation adapter is configured | **Yes.** Keep all protected access and dispatch unavailable until the selected deployment passes acceptance |
| Trusted Workspace grant administration | **6.14B** (or a dedicated preparatory integration step before 6.14D) | Prevent self-granting or permission widening without trusted administrative authority | Verified principal, tenant-scoped administration policy, Workspace configuration revisions, durable grant repository | Create, widen, narrow, list, and revoke require verified administrative authority; tenant and Workspace scope are enforced; CAS/revocation and stale-revision tests pass; ordinary users cannot grant themselves access | `WorkspaceGrantAdministrationPort` and endpoints exist; the default adapter denies every action and no production administrator integration is configured | **Yes.** No usable grant can be provisioned through production composition until a trusted administrator adapter is accepted |
| Conversation ownership and scope authorization | **6.14B**, before 6.14D activation | Isolate conversation reads/mutations and the Runs/context relationships that refer to them by principal or explicitly authorized organization scope | Trusted principal/tenant, durable conversation owner/scope model, API authorization across conversation listing/retrieval/mutation/deletion, Run relationship checks | Conversation operations and linked Run creation/list/context enforce owner or approved organization scope; foreign and cross-tenant access denies; legacy ownerless conversations fail closed or receive provenance-based migration | Conversations have no trusted owner metadata; `ConversationAccessPort` defaults to deny, so linked Run context is unavailable | **Yes.** Run ownership alone does not establish complete user/tenant isolation |
| Durable exact-operation invocation snapshots | **6.14C** | Ensure approval continuation performs only the exact operation a human reviewed, without argument substitution or fabricated reconstruction | Stable invocation identity/fingerprint, protected durable storage and access control, approval and reservation lifecycle, current-authority revalidation | Snapshot binds Run, invocation, tool ID/version, arguments, Workspace identity/revision, policy/authority revisions, and fingerprint; survives restart; missing/corrupt/mismatched/expired snapshots deny; routine inspection redacts sensitive arguments | Exact current request is process-local; raw arguments are not stored in durable approval projections, and pending requests cannot be safely reconstructed after restart | **Yes.** Do not implement approval-driven continuation or dispatch until secure restart-safe snapshots pass acceptance |

Phase 6.15 cannot be declared complete while an operational prerequisite needed by an enabled production execution path remains unimplemented or untested. Assignment to a future owner is not completion evidence. If a supported deployment profile intentionally keeps a capability disabled, document that restriction and test that it remains unavailable.
